Admin server for MI1309.github.io

Quick start (local):

1. Copy `.env.example` to `.env` and fill values. Generate a bcrypt hash for your password:

```bash
node -e "const bcrypt=require('bcrypt'); console.log(bcrypt.hashSync(process.argv[1],10));" your-password
```

2. Install dependencies, build the JSX admin pages, and start the server:

```bash
npm install
npm run build
npm start
```

3. Open the hidden admin route shown in the server output, e.g. `http://localhost:3000/admin/super-secret-route-123/login`.

Notes and security:
- The JSX admin UI is generated by `npm run build`; Express serves those generated pages through the hidden admin route and handles its session API. Do not host the admin server publicly without TLS.
- Set `SESSION_SECRET` to a strong secret in production and enable `cookie.secure` (HTTPS).
- The **Project Manager** admin page provides add, edit, delete, and save-all actions for every row on `/projects/`.
- All project rows are stored in `data/archive.json`, including JBook's table metadata. The case-study content at `/projects/jbook/` remains in `app/data/projects.js`.
- Each managed row supports `title`, `year`, `madeAt`, `description`, `technologies` (array), `url`, and optional `slug` for linking to an existing case study.
- In the Vercel setup, saving dispatches the `update-archive` GitHub Action. The static project table changes after that workflow commits the JSON and the site deployment finishes.

Deploying frontend to GitHub Pages
- GitHub Pages is static-only — server code (Express) cannot run there. You can deploy the site (HTML/CSS/JS and `data/archive.json`) to GitHub Pages as usual (branch `gh-pages` or `main`/`docs/` depending on your settings).

Recommended setup to keep admin private while hosting frontend on GitHub Pages
1. Host the static site on GitHub Pages (push repository). `data/archive.json` will be served statically by Pages.
2. Run the admin Express server on a separate machine (local/VPS). Configure the server with a GitHub Personal Access Token (PAT) and `GITHUB_REPO` in the `.env`:

```
GITHUB_REPO=youruser/yourrepo
GITHUB_PAT=ghp_... (PAT with `repo` scope to trigger dispatch)
```

3. The admin server will call the GitHub API to `repository_dispatch` an `update-archive` event. A GitHub Actions workflow (`.github/workflows/update-archive.yml`) listens for this dispatch, writes `data/archive.json`, commits and pushes the change — which updates GitHub Pages content.

Security notes for this flow:
- Keep `GITHUB_PAT` secret and only on the admin server (do NOT put it in client-side code or commit it).
- Use a minimal-scope PAT (repo) and rotate if leaked.
- Ensure admin server uses HTTPS and strong session secret.

If you prefer a purely local workflow (no Actions): the admin server can write `data/archive.json` locally and you can push the change manually from the machine where the server runs.

Deploying the Next.js admin on Vercel
1. Push the repository to GitHub and deploy it as a Next.js project on Vercel.
2. In Vercel Storage, create a **public Blob store** and connect it to this project for Production. Connect Development too if you will test uploads locally through Vercel CLI.
3. In Project Settings → Environment Variables, set `ADMIN_PASSWORD_HASH` (bcrypt hash) and `JWT_SECRET` (random signing secret) for Production.
4. Redeploy after connecting storage or changing environment variables.
5. Open `/admin/login/`; the project manager is at `/admin/project/`. Resume PDFs are stored at Vercel Blob and served through `/api/resume/file`.

Vercel Blob uses the included Hobby allowance when within its monthly limits. The SDK authenticates with the connected store's Vercel OIDC configuration or `BLOB_READ_WRITE_TOKEN`.

Security and persistence notes:
- Keep the Blob store public only because the uploaded resume is intended to be publicly viewable. The Blob write credential stays server-side.
- Resume uploads and deletion use Blob and do not require GitHub credentials.
- Project archive edits still require `GITHUB_REPO` and `GITHUB_PAT` to dispatch the existing GitHub Action. Vercel's filesystem is not persistent, so archive changes cannot be saved locally by a deployed function.
- API mutations remain protected by the admin JWT cookie.
